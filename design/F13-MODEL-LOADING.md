# F13 — load an existing model file into a scene

This record covers roadmap item F13 (2026-11-14), filed by Joel from the HootCAD reference-geometry feature: HootCAD brings existing models into its preview to design against, and Photonic could adopt geometry a caller built itself (F10) but could not load a model that already exists as a file. It says what was missing, what the public API is, and how each claim was verified, including the limits.

## What was wrong

Every way geometry entered a scene started from data the caller already held in memory: the creators build from parameters, addGeometry builds from raw arrays, and addMesh adopts objects the caller constructed with Three. A model on disk or on a server — the normal shape of reference geometry, scanned parts, and asset libraries — had no way in at all: a consumer had to fetch and parse the file itself, walk the result into the scene by hand, and re-implement the registration (transforms, shadow flags, bookkeeping) that the engine's own paths apply, ending with a second-class object the bake and the handle system only half knew about.

## The load call

scene.loadModel fetches and parses a model file and adopts the result through _adoptExternalObject, the exact registration addMesh uses, so a loaded model is a full citizen from the moment the call resolves: it sits in scene.objects under the returned standard handle, with handle transforms, material and shadow behaviour under the creators' rule applied to every mesh inside the loaded hierarchy, click handlers, removal through the handle or removeObject, and the F11 bake, which collects the loaded meshes the same way it collects an adopted group's. There is no second path to keep in sync.

The call's shapes are loadModel(url, options), loadModel({ url, ...options }), and a raw-bytes form — loadModel({ data }) or loadModel(arrayBuffer) — for callers who already hold the file's bytes (a Blob is accepted the same way). Adoption options are addMesh's whole set: position, rotation, scale, name, castShadow and receiveShadow overrides, a material override that replaces the file's materials when a caller truly wants that, the F12 physical upgrade options for a loaded finish that should carry clearcoat, disposeOnRemove, and onClick. Loading options ride alongside: resourcePath for a .gltf file whose buffers or textures live in separate files, dracoDecoderPath for Draco-compressed assets, onProgress, and onLoad and onError callbacks beside the returned promise. The handle the call returns carries the parse result as data, not as behaviour: handle.getModelInfo() (also handle.modelInfo) reports the format ('glb' or 'gltf'), the URL it came from, the animation clips and cameras the file carried, the file's own asset metadata, and the mesh count, so nothing the parser learned is thrown away even though the scene treats the model like any other object.

The first format is glTF/GLB, the web standard, which carries hierarchy and materials in one format with a binary single-file form; STL and OBJ remain named follow-on candidates, not part of this cut. Parsing is Three's GLTFLoader from three/addons, lazy-loaded on the first loadModel call the way loadSplat lazy-loads Spark, so the core library, its Node import, and consumers who never load a model file pay nothing for it. The exported helper loadGLTFModel in the new src/PhotonicModelLoader.js does the fetching and parsing and returns the parser's raw result (scene graph, animations, cameras, asset metadata) for callers who manage their own adoption; scene.loadModel is that helper plus the standard registration. Failures are named errors: a call with no source at all, a file that cannot be fetched, and a file that cannot be parsed each reject with a message that says which model and what went wrong, and onError sees the same error the promise rejects with.

## Verification

Everything below ran headlessly in Chromium with software rendering against the new examples/model-loader-demo/, whose stage is a Photonic plinth and whose model is a real file, examples/model-loader-demo/assets/reference-part.glb — a hand-built binary glTF (23,152 bytes, kept beside its .gltf JSON twin) holding a plate, a boss, and a knob in a three-level hierarchy, three materials (steel at metalness 0.85 and roughness 0.35, a red paint, a brass at metalness 1.0), and one animation, boss-spin. Twenty-one checks pass with no page errors on the demo pages or the standalone host page: the GLB loads through scene.loadModel with the info reporting format glb, the model URL, 3 meshes, the boss-spin animation, and the file's own generator string; the handle is registered in scene.objects and its root is parented to the Photonic scene, with the file's hierarchy intact under it (the model root carries Plate and Boss, Boss carries Knob) and the file's node transforms preserved (the plate sits at its authored height, the knob's world height is the sum of its ancestors' offsets plus the load position); the file's materials arrive with their names, metalness, and roughness exact and their colours distinct in the right families (glTF colours are colour-managed on load, so the check reads families rather than file hex); every loaded mesh carries cast and receive shadow flags under the creators' rule; the load call's position option and a later handle.setPosition both move the loaded root; the same model loads again from its .gltf JSON form and from raw GLB bytes through the data path, each reported with the right format; handle removal drops both the registry entry and the scene-graph node; a missing file rejects with the named load error and a call with no source rejects with its own; and the rendered captures (design/evidence/f13-model-loaded.png, read back directly: the steel plate, red boss, and brass knob legible on the plinth) prove the parsed model draws, not only registers.

The bake claim is checked on its own page load with the bake applied: scene.bakeAmbientOcclusion over the plinth plus the loaded model reports 4 receiving meshes and 707 vertices — the loaded model's three meshes and their vertices are inside those counts, where the plinth alone is one mesh — with 5,120 ground texels shaded under the combined footprint and a mean visibility of 0.69, and the baked capture (design/evidence/f13-model-baked.png) shows the contact shading pooled around the loaded plate. Bake cost for that scene was about 0.73 seconds in-browser on the software rasterizer, the F9/F11 order. Regression checks: the library entry imports in Node with all 30 exports (loadGLTFModel is the one new export; the rest of the surface is the new scene method and its types), every source file passes node --check, a strict TypeScript 5 consumer using loadModel in all three call shapes, getModelInfo, and the exported helper compiles clean against src/index.d.ts, and npm pack --dry-run lists 58 files including src/PhotonicModelLoader.js, the demo with both model files, and this record.

## Limits

Animations are carried and reported, not played: the engine has no animation mixer in its render loop, so a consumer who wants a loaded clip to move drives an AnimationMixer over handle.getMesh() with the clips from getModelInfo().animations, the standard Three pattern. That is a deliberate line — F13 is about getting the model into the scene as a full citizen, and playback policy (which clip, looping, blending) is the consumer's call. Skinned meshes and morph targets parse and adopt like any other mesh, with the creators' shadow rule applied; nothing in the load path special-cases them. Textures the file references are the loader's business exactly as in raw Three: embedded and same-folder resources resolve on their own, and resourcePath covers the rest. The studio environment and physical upgrade compose with loaded models through the ordinary paths — setStudioEnvironment lights a loaded metal part the same as an adopted one, and passing clearcoat in the load options upgrades the loaded materials through the F12 adoption rule — but neither is on by default, because a reference model's own materials are its author's statement. Nothing was pushed to GitHub and nothing was published to npm; the release decision is Joel's, and the docs site's vendored library copy refreshes through docs/refresh-vendored.mjs when the release is cut, as it did for 0.2.0 through 0.4.0.

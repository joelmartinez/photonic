# F14 — model loading grows to STL and OBJ

This record covers roadmap item F14 (2026-11-14), the follow-on F13 named when it landed glTF/GLB model loading: F13's record closed by calling STL and OBJ the follow-on candidates, and this item builds them. It says what was missing, what the public API is, and how each claim was verified, including the limits.

## What was missing

scene.loadModel spoke exactly one format family. A model that exists as an STL — the shape CAD tools, slicers, and scan pipelines hand around most — or as an OBJ, the other long-lived interchange shape, still had no way in: a consumer had to fetch and parse the file itself and then adopt the result through addMesh by hand, re-implementing the format choice, the material question, and for OBJ the material-file fetch that the format expects to travel with the model. The load call now speaks all three families through the one entry point, and the adoption is the same registration F13 used, so nothing about a loaded model's standing in the scene depends on which format it arrived in.

## The load call, per format

The call's shapes are unchanged — loadModel(url, options), loadModel({ url, ...options }), and the raw-bytes forms — and the format is chosen honestly per file: an explicit format option wins, then the URL's extension, then the data's own content (the glTF binary magic, an ASCII STL's opening solid line, a binary STL's exact size equation, a JSON opening for glTF, OBJ's line keywords), with glTF as the default the F13 path always used. The parse result rides on the handle through getModelInfo() the same way for every format, with format naming the file that actually loaded — 'glb', 'gltf', 'stl', or 'obj' — and the fields a format cannot fill reported as what they are: STL and OBJ carry no animations, cameras, or asset metadata, so those come back empty or null rather than invented, and OBJ adds materialLibraries naming the material files its text declared while STL adds hasColors for the binary colour case below.

STL is parsed by Three's STLLoader, lazy-loaded on first use the way the GLTF loader is, and both encodings ride the one path because the loader itself reads binary and ASCII from the same bytes. STL carries no materials and no hierarchy, and the record says so plainly: the parsed geometry arrives as a single mesh wearing the engine's default material treatment — the same default addGeometry builds with, a MeshStandardMaterial in light machine grey at roughness 0.65 and metalness 0.15 — with per-vertex colours honoured when a binary file carries them in the Magics colour form. That default is a starting surface, not a second-class one: the adoption material override replaces it, the F12 physical options upgrade it, and three load options (color, roughness, metalness) steer it for callers who know the finish they want, because the file itself has nothing to say about any of them.

OBJ is parsed by Three's OBJLoader, also lazy-loaded, with its material file handled the way the format carries one: the OBJ text's mtllib names resolve against the OBJ's own folder (or resourcePath when the caller sets one) and load through MTLLoader before the parse, so the file's groups arrive as named meshes wearing their MTL materials, exactly as a glTF model's groups arrive wearing theirs. A caller can name the material file directly with mtlUrl, supply its text with mtlData for the raw-bytes form where no folder exists to resolve against, or turn material loading off with loadMaterials: false. The exported helpers loadSTLModel and loadOBJModel sit beside loadGLTFModel for callers who want a parsed result raw; scene.loadModel is those helpers plus the standard registration. Failures stay named errors per format — a missing STL, a missing OBJ, and a missing material file the caller named explicitly each reject saying which file and what went wrong, and onError sees the same error the promise rejects with.

## Verification

Everything below ran headlessly in Chromium with software rendering against the extended examples/model-loader-demo/, whose plinth now carries four real files side by side: the F13 binary glTF reference part, a hand-built binary STL bracket (a base plate and an upright, 24 triangles), a hand-built ASCII STL wedge (a triangular prism, 8 facets), and a hand-built OBJ knob (two groups, base and top, taking a dark body and an orange top from its knob.mtl). Thirty-five checks pass with no page errors on the demo pages or the standalone host page: the glTF load is unchanged (format glb, 3 meshes, the boss-spin animation, the file's generator string); both STL files report format stl with one mesh each and the exact triangle counts their files carry, wear the default material with its exact colour and roughness and metalness values, carry cast and receive shadow flags under the creators' rule, and take the load call's position and rotation options; the OBJ reports format obj with materialLibraries naming knob.mtl, its base and top groups survive as named meshes, the two MTL colours arrive applied as two distinct material colours in the right families, and every mesh carries the shadow flags. The raw forms all load in-page: binary STL bytes sniffed as stl with no name to go on, ASCII STL as text and as a Blob, OBJ as text with its material supplied through mtlData, OBJ as bytes under an explicit format, and OBJ text with no hint at all sniffed by its own lines; the STL colour and roughness options steer the default material, a clearcoat load option upgrades an STL load to a physical material through the F12 rule, and every extra load removes cleanly back out of the registry. The error paths reject with their named errors, including the explicit-material-file case. The rendered captures (design/evidence/f14-stl-obj-loaded.png, read back directly: the steel plate, red boss, and brass knob in the centre, the grey bracket and wedge in front wearing the default material, the dark knob with its orange top at the back left) prove the parsed models draw, not only register.

The bake claim is checked on its own page load with the bake applied: scene.bakeAmbientOcclusion over the plinth plus all four loaded models reports 8 receiving meshes and 1,283 vertices — the STL bracket, the STL wedge, and the OBJ knob's two meshes are inside those counts alongside the glTF model's three — with 5,422 ground texels shaded under the combined footprint, and the baked capture (design/evidence/f14-stl-obj-baked.png) shows the contact shading pooled on the plinth around each model. Regression checks: the library entry imports in Node with all 32 exports (loadSTLModel and loadOBJModel are the two new ones; the rest of the surface is the widened scene method and its types), every source file passes node --check, a strict TypeScript 5 consumer using all three helpers, the new load options, and the widened info shape compiles clean against src/index.d.ts, the declarations were cross-checked against the runtime exports with none missing in either direction, and npm pack --dry-run lists the package with the new demo assets and this record included.

## Limits

STL's flatness is the format's, not a choice the engine can undo: one geometry, no groups, no materials, no units declaration, so a loaded STL is one mesh in the default material until the caller says otherwise, and a file authored in millimetres arrives a thousand times larger than the same part authored in metres — scale is the caller's option, as it is for every load. OBJ's materials are the MTL shading model (the loader builds Phong materials from them), not the physical surface glTF carries; the F12 upgrade options compose with an OBJ load when a caller wants clearcoat over them. A material file an OBJ names but the server has lost does not fail the load — the geometry still arrives with the OBJ loader's own default materials — because a reference model with plain materials is still the reference model; only a material file the caller named explicitly fails loudly, since that caller stated a requirement. OBJ lines and points (files that carry wireframe or point-cloud elements) parse through the loader but are not meshes, so they do not register, cast, or bake; the adoption is a mesh adoption, as it has been since F10. Textures an MTL file references resolve through the material loader against the OBJ's folder or resourcePath, as in raw Three. Nothing was pushed to GitHub and nothing was published to npm; the release decision is Joel's, and the docs site's vendored library copy refreshes through docs/refresh-vendored.mjs when the release is cut, as it did for 0.2.0 through 0.5.0.

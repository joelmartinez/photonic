# F7 — shadows: root cause, defaults, and verification

This record covers roadmap item F7 (2026-11-12). It says what was actually wrong, what the engine now does by default, and how both halves were verified.

## The reported defect was a viewpoint artifact, not an engine defect

The filing session reported that shadow receiving never happens in a Photonic scene: with every flag set correctly at runtime, the caster was rendered into the light's shadow map, yet no receiving surface ever darkened, and the same failure appeared with a brand-new light, plane, and cube created from the scene's own Three.js instance, while a minimal standalone Three.js page rendered the shadow correctly. This session bisected that claim headlessly in three independent setups, and shadow receiving worked in every one of them: in this repo served natively with an import map (flags set before the first frame, and again with flags flipped at runtime after frames had already rendered, the filing session's exact recipe), in the codecube.net integration project's own shipped site build driven with its diag8 runtime-flags driver, and with a brand-new light, white plane, and cube created from the scene's own Three.js instance inside a Photonic page (the filing session's diag5 pattern). In each case the floor pixels inside the shadow read clearly darker than lit floor pixels nearby (luminance about 88–94 against 126–133), and the captures show a plain cast shadow. The evidence captures are in design/evidence/: f7-q1-site-build-diag8.png is the filing project's own before-build with its own runtime-flags recipe, and f7-raw-light-plane-cube.png is the new-light, new-plane, new-cube pattern.

The reason the filing session saw no shadow is geometry, not code. Every one of its captures used Photonic's default camera, which sits at (2, 1.5, 2), on the same side of the scene as the default directional light at (5, 10, 7.5). A shadow falls on the far side of the object that casts it, so from that camera the box's shadow lands behind the box and is hidden by the box itself; almost no part of it is visible in the frame at all. The floor pixel samples the filing session compared were both lit points, so they matched, which read as "receiving is dead." Its minimal standalone page used a near-frontal camera, from which the same shadow peeks out beside the cube, so the comparison looked like an engine difference when it was a camera difference. Moving the camera to the shadow side, at (-3, 2.5, -3) looking at the origin, makes the shadow plainly visible in the shipped build with no engine change at all, which is the capture in f7-q1-site-build-diag8.png.

The practical lesson is recorded here so it is not relearned: when checking a shadow from a light, put the camera on the opposite side of the caster from the light, or sample a floor point that is both inside the shadow volume and visible to the camera; a point behind the caster from the camera's view samples the caster, not the floor.

## The real gap was defaults, and that half was exactly as filed

The filing session's code reading was correct: the renderer enabled PCF soft shadow maps and the grid floor received, but no engine light was ever set to cast and no created object was ever set to cast or receive, so a standard scene showed no shadow because nothing asked for one. That is the half this session changed in src/PhotonicScene.js. The default directional light now casts by default, with a 2048-pixel shadow map, a shadow camera fitted to the stage (seven metres each way, near 1, far 30), a small negative bias and normal bias against surface acne, and its target added to the scene. The box, sphere, cylinder, and plane creators (the wall creator builds on the plane) now set cast and receive on every object they make; casting turns itself off for a transparent or emissive material, because those should not throw a solid shadow, and either flag can be set explicitly per call with the castShadow and receiveShadow options, or changed later through the handle's setCastShadow and setReceiveShadow. The point and spot light creators take castShadow and shadowMapSize options (off by default, because point shadows cost six renders), and every light handle gains setCastShadow and getCastShadow. The type declarations in src/index.d.ts cover the new options and handle methods.

## Verification

The headline check is a Photonic scene that touches no shadow flag anywhere: a box and a sphere created with the ordinary creator calls, lit only by the default lights, captured headlessly in design/evidence/f7-box-shadow.png. Both objects cast a soft shadow onto the grid floor, the sampled floor luminance inside the box's shadow is 94 against 128–129 on lit floor nearby, and the in-page state confirms the defaults did it (light casting with a 2048 map, both meshes cast and receive true, floor receive true). The camera for this capture stands at (-3, 2.5, -3), the shadow side, for the reason given above. Regression checks: the library entry still imports in Node with all 28 exports, and the standalone host page still loads the box module through the scene loader with no page errors, so the standalone-consumption shape consumers use is intact. Nothing was pushed to GitHub and nothing was published to npm; the mirror snapshot follows the usual interactive route after a roadmap-level stage.

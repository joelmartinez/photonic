# Photonic — virtual camera mode (F2, 2026-11-10)

PhotonicVirtualCamera, in src/PhotonicVirtualCamera.js and exported from the library entry, turns what Photonic renders into a live video stream: any PhotonicScene, any single canvas, a PhotonicOverlay on its own, or the full composite of a video element with its overlay drawn on top, and the consumer gets back an ordinary MediaStream with one video track that it can use anywhere a browser accepts a stream.

The consumer pattern is deliberately small, and it is the whole contract: build the camera from the source you want to show, ask it for the stream once, and then hand that stream to the place that should show or send it, for example setting it as the srcObject of a video element so the person sees the emitted picture, passing it to an RTCPeerConnection as a WebRTC source, or recording it, which the class also wraps directly with startRecording and stopRecording returning a Blob the consumer can play back or download.

A plain scene and a single canvas are captured straight from their own canvas, with no extra copy step, so what the stream shows is exactly what the canvas shows at the requested frame rate. The overlay composite is different by necessity, because the video and the overlay live in two separate elements stacked by the page, so the class draws both, in page order, into one output canvas on each animation frame and captures that canvas instead; the output size follows the video's own size, and a consumer who needs a fixed output size passes width and height explicitly.

The honest label matters, and the class states it in code as well as here: getInfo reports kind browser-captured-stream and isOSVirtualCameraDevice false, because that is the truth. A browser captured stream works only inside browser code that accepts a MediaStream, so a web app can show it, send it over WebRTC, process it, or record it, but it does not appear in a browser's camera picker and it does not appear as a camera in Zoom, Teams, OBS, or any other app on the computer. Making a stream that those apps can pick would need a native companion program installed on the person's computer that registers a real virtual camera device with the operating system and feeds it these frames, and that companion is a separate, later piece of work that Photonic does not claim to do.

That limit still leaves the main uses Joel named fully working in the browser: a KataPose creator can emit the clean skeleton-over-video composite as their class camera feed to a WebRTC call or a recording, and a Vomitorium run can emit its spectator view the same way, because in both cases the thing receiving the feed is browser code, not an operating system camera menu.

The runnable proof is examples/virtual-camera-demo/, a page that plays the same synthetic video feed the overlay demo uses, draws the default pose skeleton over it, emits the composite through PhotonicVirtualCamera, and shows the resulting stream live in a second video element beside the source, with a record control that captures two seconds of the stream and makes it playable and downloadable on the same page; the same page can also build a plain PhotonicScene with a box in it and emit that scene as a stream, which is how the verification proved the scene path and not only the composite path. The verification performed for F2, including the headless checks on the stream, the composite pixels, the second video element playing, the recording, and the scene stream, is recorded in PROGRESS.md.

Two practical limits are worth knowing before a consumer leans on this: the frame rate is a request the browser tries to honor rather than a promise, and a hidden or throttled page may deliver fewer frames, and the composite path costs one full-frame copy per frame, which is the right price for a clean picture at ordinary video sizes but is not free at very large resolutions.

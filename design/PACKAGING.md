# Photonic — packaging (P1, 2026-11-10)

This record says what the published package is, what is inside it, and how versions are handled, so the publish gate is a decision and not a scramble. The library was made package ready without being published: publishing happens only on the owner's explicit word, in an interactive session, with the owner's npm credentials.

The package is @codecube/photonic, an ES module package (type module) whose runtime is plain JavaScript in src/ with no build step, so what a consumer installs is exactly the code in this repo. The peer dependency is three at ^0.170.0, which the consumer installs and resolves; the one ordinary dependency is @sparkjsdev/spark at ^0.1.10, lazy-loaded only when a splat is loaded. Node 18 or newer is the stated floor for tooling, and the library itself runs in browsers with WebGL, import maps, and canvas capture support.

The exports map in package.json is the public contract. The root entry (@codecube/photonic) points at src/index.js with types at src/index.d.ts, and two subpaths cover the feature modules on their own: @codecube/photonic/overlay for PhotonicOverlay and its helpers, and @codecube/photonic/virtual-camera for PhotonicVirtualCamera and its helpers, each with its own declaration file that re-exports the matching slice of the root types; @codecube/photonic/package.json is also exported so tooling can read the manifest. The older main and module fields stay, pointing at the same entry, for resolvers that do not read exports maps. Imports inside the package use relative paths with .js extensions throughout, so nothing depends on this map for the library's own files, and consumer code that imports the package name today against the peer checkout will import the published package unchanged after the flip.

The type declarations in src/index.d.ts are hand-written against the runtime, not generated, because the sources are plain JavaScript. They cover every export of the entry (the eight engine classes, the overlay class, its two helper functions, its style object and pose constants, the virtual camera class, its three helper functions and kind constant, the splat camera estimator, and the three XR pose math functions) plus the shapes consumers actually touch: scene object and light handles, the splat handle, loader module shape, overlay pose inputs in all the accepted forms, overlay style, and the virtual camera options and info records. Three.js objects that cross the API are typed structurally or as unknown on purpose, because the three package ships no bundled types and forcing consumers to install a separate type package for Photonic's sake would be wrong. The declarations were verified two ways for P1: a runtime check that every name the declarations promise exists on the real module with the right kind, and a TypeScript compile of a small consumer that imports the root and both subpaths and uses the headline APIs.

What ships is set by the files allowlist in package.json, and the allowlist is the whole story because npm always adds package.json, the README, and the license on its own. The tarball carries src/ (runtime and declarations), the runnable examples (examples/modules/, examples/host-page/, examples/quickstart/, examples/overlay-demo/, and examples/virtual-camera-demo/), the note that explains the unsupported examples without shipping their code (examples/unsupported/README.md), the two feature design records (design/OVERLAY.md and design/VIRTUAL-CAMERA.md), this packaging record, and the changelog. It deliberately leaves out the extraction notes, the decoupling plan and audit material, the progress and roadmap working files, the chain instructions, and the unsupported example code, because none of that is something a consumer runs. The P1 session inspected the packed tarball file by file against this intent and recorded the listing in PROGRESS.md, and then installed that tarball into a clean folder and ran the quickstart scene from it in a headless browser, which is the proof that the allowlist did not cut anything the library needs.

Version discipline is simple and is stated in CHANGELOG.md where consumers will see it: Semantic Versioning, the version field in package.json is the single source of truth, every change that will ship is written into the changelog's Unreleased section in the same commit that makes it, a release renames that section to the new version with its date before publishing, and breaking changes to the public exports are called out in the changelog in plain words. The version prepared by P1 is 0.1.0, the first package-ready build; it stays unpublished until the gate clears, and the post-publish consumer flip (roadmap C1) changes only each consumer's dependency line, never its imports.

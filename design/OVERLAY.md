# Photonic — clean overlay rendering (F1, 2026-11-10)

PhotonicOverlay, in src/PhotonicOverlay.js and exported from the library entry, draws pose skeletons and similar annotation graphics over a video element and nothing else: it owns a separate transparent WebGL renderer whose canvas sits exactly over the video's displayed content area, with a clear alpha of zero, no scene background, no grid, no lights, and no debug helpers, so the default picture is only the graphics the consumer asked for, composited over the video by ordinary page stacking.

The mapping is resolution independent by construction: poses arrive in normalized video coordinates (x to the right and y down, both 0 to 1 in the frame, with z as a relative depth in the same units), an orthographic camera spans a world two units tall and as wide as the video's aspect ratio, and the renderer sizes its backing store from the displayed size times the device pixel ratio, so the same pose lands in the same place at any window size, any pixel density, and any video resolution, and a resize changes only the backing store, never the world positions.

Stability is a consequence of the same design: joint and bone positions are exact functions of the pose most recently handed to setPose, with no random elements, no physics, and smoothing off by default (a consumer may opt into smoothing through the constructor, knowing it trades a little exactness for softness), so feeding the same pose twice produces pixel-identical output, and any motion in the overlay is motion in the data itself.

Poses are accepted in the shapes pose estimators already produce: an object keyed by joint name, an array in COCO 17 order, or a wrapper object carrying either under a joints or keypoints field, with optional per-joint confidence (joints below the style's confidence threshold, and their bones, are hidden) and optional per-joint deviation data described below; normalizePose is exported for consumers who want the normalized form themselves. The default bone set is POSE_CONNECTIONS over the COCO 17 joint names, and a consumer with a different skeleton passes its own connection pairs to the constructor.

The default style is the KataPose MVP look Joel set on 2026-11-10: bones are translucent cylinders in a cyan-blue scheme with a slightly larger, fainter back-side shell around each one that reads as an outline, joints are small spheres in the same family with a larger additive halo that reads as a glow, and the geometry stays simple on purpose, with no anatomical bone models; every value behind that look (colors, opacities, radii, the glow scale, the outline scale) lives in DEFAULT_OVERLAY_STYLE and can be overridden through the constructor or setStyle, in whole or per key.

Deviation display, for showing how far a student's pose sits from a reference pose, is built from two primitives that can be used together or separately: a consumer either sets a target pose (through setTargetPose or the setPose options), in which case each joint's offset is the target minus the actual position, or supplies an offset vector or a deviation magnitude directly on a joint. Per-joint color encoding maps the offset magnitude through deviationColorHex, holding the base cyan at and below the warn threshold, blending toward yellow up to the alert threshold, and reaching red beyond it, and the same tint is applied to a bone when either of its endpoints carries the larger deviation. Arrow glyphs draw a shaft-and-cone arrow from the actual joint along its full 3D offset vector, so the arrow's direction is the offset's direction and its length is the offset's length in world units, colored by the same deviation ramp unless the offset is within tolerance, in which case it uses the style's neutral arrow color; arrows can be toggled with setShowArrows and color encoding with setColorByDeviation, which is exactly the switch the KataPose review experiment needs to compare color-only against arrows.

The runnable proof is examples/overlay-demo/, a page that plays a synthetic canvas-captured video stream (so the demo needs no camera and no video asset) and draws the default skeleton over it, with three joints offset from a target pose so both deviation primitives are visible and two checkboxes that toggle them; opening it with ?still=1 freezes the pose for screenshots and tests. The verification performed for F1, including the headless checks on counts, colors, arrow direction, stability, and resize behaviour, is recorded in PROGRESS.md.

One honest limit: the overlay aligns to the video element's content rectangle, accounting for object-fit contain, cover, and fill, but it does not track per-frame video effects such as CSS transforms or picture-in-picture, and z is a relative depth used for arrow direction and joint placement in the overlay's own world, not a calibrated camera-space measurement; turning normalized pose depth into true 3D is the pose estimator's job, not the renderer's.

# Photonic — decoupling plan (D1 audit, 2026-11-10)

This plan maps every coupling between Photonic and its original host, the Static-Site-Generator (SSG) that runs codecube.net, and gives D2 an ordered fix list. Every claim below was verified by reading the actual files in this repo on 2026-11-10 (`src/`, `examples/modules/`, `package.json`, and the two files in `extraction-notes/`), not from the extraction notes alone. Where a coupling named in DESIGN.md no longer matches the code, this plan says so plainly. The headline finding is simple: the core engine files are already clean, and almost every coupling lives in the entry point, the module loader, and the examples — which is good news, because those are exactly the parts D2 was always going to rewrite.

## What is already clean

The nine engine files (`PhotonicScene`, `PhotonicRenderer`, `PhotonicCamera`, `PhotonicXRManager`, `PhotonicControlSystem`, `PhotonicInput`, `PhotonicGrid`, `splatCameraHeuristics`, `xrPoseMath`) import nothing outside this repo except `three` (a declared peer dependency) and, inside `PhotonicScene.loadSplat`, `@sparkjsdev/spark` (a declared dependency). They assume no host DOM ids, no host URLs, and no host globals beyond ordinary browser APIs (`window` resize and device pixel ratio, `document` listeners, `navigator.xr`), which any consumer page provides. `splatCameraHeuristics.js` has no imports at all. Nothing in `src/` or `examples/` uses React, JSX, or any SSG service. The `extraction-notes/` folder is reference material only and is not a runtime coupling; D2 should leave it in place and out of the published file set.

## The couplings, in the order D2 should fix them

### C1 — Extensionless relative imports rely on the host's webpack resolver (fix first; it blocks everything else)

`src/PhotonicScene.js` imports six sibling files with no extension (`./PhotonicCamera`, `./PhotonicRenderer`, `./PhotonicGrid`, `./PhotonicInput`, `./PhotonicXRManager`, `./PhotonicControlSystem`), `src/PhotonicXRManager.js` imports `./xrPoseMath` the same way, and `src/index.js` imports four siblings the same way. This worked in the SSG because its webpack config sets `resolve.extensions: ['.js', '.jsx']` (verified in `extraction-notes/ssg-webpack.config.js`). Native browser ES modules and Node both refuse extensionless relative imports, so today not even the clean engine files can load outside a bundler that mimics webpack. In a standalone consumer this breaks at the first import, before any host-specific code is even reached. Fix approach: sever the assumption — add the `.js` extension to every relative import in `src/` (and in the examples, per C6 and C7). This is mechanical, touches eleven import lines, and is the prerequisite for every later step and for the standalone test.

### C2 — The package entry point is the host's /viz page, including a missing Modulation import

`package.json` names `src/index.js` as `main`, and that file is not a library entry — it is the SSG's /viz page script. It imports `Modulation`, `ModulationSystem`, `Modulator`, and `createPhotonicFrameContext` from `../modulation/index.js` (lines 10–15), a file that does not exist in this repo, so the package's declared entry point cannot be imported at all in a standalone consumer; the import fails before any other problem matters. DESIGN.md's coupling #1 is confirmed exactly as noted. The same file also auto-runs on `DOMContentLoaded`, does nothing unless an element with id `photonic-container` exists, reads the module choice from the `?module=` URL parameter, reads a cache-busting version from the container's `data-site-version` attribute, wires page elements with host ids (`viz-module-select`, `viz-xr-controls`, `viz-enter-xr`, `viz-xr-status`, and a `.nav-module-picker` wrapper), and publishes the API as the `window.Photonic` global. All of that is correct behaviour for codecube.net and wrong for a library: a consumer importing the package gets a page script that silently no-ops on their page, or crashes on the missing Modulation import. Fix approach: sever. D2 splits this file in two — a new library entry that only exports the engine classes, the loader, the pose math, and the splat heuristics, with no DOM access, no auto-run, and no Modulation re-exports; and the existing page wiring moved, unchanged in behaviour, into a demo host page under `examples/` where host ids and `window.Photonic` belong. The Modulation names are dropped from Photonic's public surface rather than stubbed, because nothing in the engine itself uses them (verified: the only Modulation references in `src/` are this import and its re-export on `window.Photonic`). `package.json` then points `main` at the new library entry; the fuller exports map and packaging polish stay with roadmap item P1, but the entry repoint is D2 work because the standalone test imports through it.

### C3 — The module loader hard-codes the SSG's output path and can only load classic scripts

`PhotonicSceneLoader._buildModuleUrl` builds every module URL as `/script/photonics/<name>` on the current origin, which is the SSG's build output layout, not anything a standalone consumer has: the SSG webpack config emits each scene module as its own bundle into `CodeCubeConsole/out/script` with photonics modules in a `photonics/` subfolder (verified in `extraction-notes/ssg-webpack.config.js`). The loader also takes a `siteVersion` option that exists only to cache-bust against the host page's build version. In a standalone consumer, every `loadModule` call requests a path that does not exist and fails. The deeper problem is the loading mechanism itself: `_loadScript` injects a classic `<script>` tag and then looks the module up in the `window.PhotonicModules` registry, which means a module file must be a self-contained classic script with no imports of its own — true in the SSG only because webpack pre-bundled each module into exactly that shape. Three of the six shipped examples (`splat`, `audio-demo`, `synth-designer`) are ES modules with top-level `import` statements and cannot execute as classic scripts at all, so the current loader cannot load half the examples even if the URL were fixed. DESIGN.md's coupling #4 (webpack-based discovery) is confirmed, with this sharpening: the webpack dependency is not only discovery, it is also the per-module bundling that made the registration contract work. Fix approach: internalize a real loader story. D2 changes the loader to fetch modules with dynamic `import()` from a configurable base — a constructor option such as a module base URL or an explicit name-to-URL map, defaulting to a relative `./modules/` beside the consuming page — and modules become ordinary ES modules that export `Load`, `Update`, `Unload`, and `Metadata`. The `window.PhotonicModules` registration at the bottom of each example is kept working as a compatibility shim during D2 (the loader checks the registry after import for modules that registered instead of exporting), and the hard-coded `/script/photonics/` path and the `siteVersion` option are removed. Module-name validation (the existing `^[a-zA-Z0-9_-]+\.js$` check) stays.

### C4 — A library helper returns the host's page URL

`src/moduleSelector.js` exports `getModuleNavigationUrl`, which builds `/viz/?module=<name>` — the SSG's page path baked into a file that ships as part of the library. `syncModuleSelector` and `wireModuleSelector` are generic select-element helpers, but the navigation target is pure host knowledge. In a standalone consumer this file is either dead weight or, worse, navigates the user's page to a `/viz/` path that does not exist. Fix approach: sever — this file leaves the library entry with the rest of the page wiring in C2 and moves to the demo host page, where a `/viz/`-style URL is that page's own business. If a future consumer wants selector syncing, the two generic helpers can return as library utilities with the navigation URL supplied by the caller; D2 does not need them.

### C5 — Spark is declared loosely and its error message points at the host's package file

`PhotonicScene.loadSplat` lazy-loads `@sparkjsdev/spark` with a webpack magic comment (`/* webpackChunkName: "spark" */`), which other bundlers and browsers simply ignore, so it is harmless but is host-build residue. The real couplings are that `package.json` declares the dependency as `"*"` — any future version, untested — while the SSG pinned `^0.1.10` (verified in `extraction-notes/ssg-frontend-package.json`), and that the failure message tells the user to make sure the package "is listed in frontend/package.json and the frontend has been built", which is SSG build instructions leaking into a library error. Fix approach: declare it properly — pin `@sparkjsdev/spark` to `^0.1.10` in `package.json`, drop the magic comment, and rewrite the error message to name this package's own dependency. The `three` peer declaration (`^0.170.0`) already matches the SSG's version and needs no change, but D2 must state how a standalone consumer resolves the bare `three` and `three/examples/jsm/...` specifiers the engine uses — the test definition below uses an import map, which is also the story the README quickstart will document at P1.

### C6 — The examples' registration contract is a host global, and one DESIGN.md claim about example imports is stale

All six examples end with an immediately-invoked block that registers `{ Load, Update, Unload, Metadata }` on the `window.PhotonicModules` global, because that is what the loader in C3 reads. That global is a workable contract, but it is a host-page convention rather than a module system, and it is why the examples cannot simply be imported. Fix approach: internalize — as part of C3, each supported example also (or instead) uses real ES module exports, keeping the registration block as a shim so the SSG-shaped usage keeps working during the transition. One correction to DESIGN.md matters here: its coupling #3 says example modules import engine helpers via SSG-relative paths (`../viz/...`), plural and general. Verified against the files, exactly one example does that — `splat.js`, covered as C7. `box.js`, `solar-system.js`, and `liminal.js` contain no imports at all; `audio-demo.js` and `synth-designer.js` import from `../modulation` and `../sonance`, not `../viz`. D2 should not budget a general example-import remap that the code does not need.

### C7 — splat.js imports through a path that does not exist here, and defaults to a host asset

`examples/modules/splat.js` line 1 imports `estimateSplatCamera` from `../viz/splatCameraHeuristics` — the SSG's folder layout, where the engine lived in `frontend/src/viz/` and the modules in `frontend/src/photonics/`. In this repo that path resolves nowhere; the file it wants is `src/splatCameraHeuristics.js`. The import is also extensionless (C1). Separately, the module's default configuration loads its splat asset from `/assets/scans/room.spz`, the host site's asset path, and its header comment tells the reader to place the file in `CodeCubeConsole/out/assets/scans/` — no such asset ships in this repo, so the example cannot show anything out of the box in a standalone consumer even after its import is fixed. Its configuration channel, the `window.PhotonicSplatConfig` global, is documented and guarded (`typeof window !== 'undefined'`), and counts as the module's public contract rather than a hidden coupling; D2 keeps it. Fix approach: remap and declare — point the import at the library (`../../src/splatCameraHeuristics.js` while examples live in this repo, settling to the package name once P1 sets the exports map), add the extension, remove the host asset path as a default so the URL is config-supplied with a clear error when absent, and rewrite the header comment to describe standalone use.

### C8 — audio-demo.js is a Sonance demo, not a Photonic demo: unsupported list

`examples/modules/audio-demo.js` imports `createPhotonicFrameContext`, `distance3D`, and `normalizeToUnit` from `../modulation/index.js` (missing here), and at runtime requires the `window.Sonance` global, which the host page supplied by loading its `sonance.gen.js` bundle; without it, `Load` logs an error and returns an empty state, so the scene never builds. The module's whole subject is the Sonance engine's modulation system driving Photonic visuals — Photonic is the guest in this demo, not the host. Two of the three missing imports (`distance3D`, `normalizeToUnit`) are tiny pure math helpers that D2 could internalize into the example in minutes, but that does not save it: `createPhotonicFrameContext` feeds Sonance's `modulation.update`, and what that function must return can only be verified against the Modulation source, which is not in this repo — from the call sites here, only `frame.camera.position` is provably consumed. Fix approach: drop to the explicitly unsupported list. D2 moves `audio-demo.js` to `examples/unsupported/` with a short note in that folder and in the README stating it requires the Sonance and Modulation workstreams, which are not part of Photonic, and that it is kept for reference. The same treatment applies to its minor soft coupling: its UI panel looks for a host-provided `#photonic-ui-overlay` element and falls back to `document.body`, which needs no fix once the file is out of the supported set.

### C9 — synth-designer.js depends on Sonance twice over: unsupported list, with a noted salvage path

`examples/modules/synth-designer.js` imports `SonanceSceneManager` from `../sonance/SonanceSceneManager.js` and `createPhotonicFrameContext` from `../modulation/index.js`, both missing here, so the file cannot even be parsed as a module in a standalone consumer. Its 3D editor half is more independent than audio-demo's: `Load` builds the node scene without Sonance, and the audio start path warns and returns when `window.Sonance` is absent. But scene save, load, list, download, and upload all go through `SonanceSceneManager` (five call sites, lines 892–923), and playback goes through the Sonance engine and its modulation system, so the module's core purpose still sits on the missing workstream. Fix approach: drop to the explicitly unsupported list alongside audio-demo, for the same reason. The plan records one salvage path for a later roadmap item, not D2: the scene manager's used surface is small (save, list, load, download, upload of JSON scene definitions) and could be re-implemented inside the example with `localStorage` and blob download/upload, and the frame-context call has the same shape as in C8 — if Joel ever wants this editor standalone, that is a small, bounded job, but it is not decoupling, it is feature work.

### C10 — liminal.js has a Sonance dependency the extraction notes never mentioned — and it is already optional

DESIGN.md names only audio-demo and synth-designer as Sonance-dependent. Verified in the files, `examples/modules/liminal.js` also builds its ambient audio on `window.Sonance` (its `createLiminalAudio` expects the host's `sonance.gen.js`). The difference is that liminal treats audio as an enhancement: when Sonance is absent it logs an error and returns, every later audio call guards on the engine being null, and the explorable scene — the module's actual content — loads and runs fully. So liminal belongs in the supported set, and reporting it as broken would be wrong. Two small fixes: change the missing-Sonance log from an error to a plain informational line so a standalone run does not look like a failure, and document Sonance as an optional integration for this module. Liminal also reads its THREE reference as `scene.THREE ?? window.THREE` (line 2130); `scene.THREE` is set by the `PhotonicScene` constructor and always wins, so the `window.THREE` fallback is a leftover host-global assumption — harmless today, and D2 removes it so the supported examples read no host globals at all. Liminal's other host-adjacent behaviour (its own key listeners, canvas textures) uses only standard browser APIs and the scene object it is handed, and is not a coupling.

### C11 — Host page structure the entry point assumes (documented so the demo page owns it)

Beyond C2, the page wiring assumes a specific host document: a container that starts with a `photonic-loading` class the script removes, XR controls that may or may not exist (this part is properly guarded and returns early when absent), and a module `<select>` whose option values are module file names. None of this is wrong — it is a page's contract with its script — but none of it is in this repo today, so there is currently no runnable page in the repo at all: no HTML file exists anywhere in the tree. Fix approach: internalize as a demo — the host page D2 creates under `examples/` ships the HTML that provides these ids and classes, so the contract becomes something this repo owns and the standalone test can run, instead of something inherited from codecube.net's templates.

## Recommended D2 execution order

D2 executes in this order, and each step leaves the repo working: (1) C1, add `.js` extensions to all relative imports in `src/`; (2) C2 and C4, split the library entry from the page wiring, move the page wiring and `moduleSelector.js` into a new `examples/host-page/` demo with its own HTML (C11), and repoint `package.json` `main` at the library entry; (3) C5, pin Spark, drop the webpack comment, fix the error text, and settle the import-map story for `three`; (4) C3 and C6, rewrite the loader around dynamic `import()` with a configurable module base, convert the supported examples (`box`, `solar-system`, `liminal`, `splat`) to ES module exports with the registration shim kept, and remove the `/script/photonics/` path and `siteVersion`; (5) C7, remap the splat import, remove the host asset default, and fix its header comment; (6) C10, soften liminal's Sonance log line, document the optional audio, and remove its `window.THREE` fallback; (7) C8 and C9, move `audio-demo.js` and `synth-designer.js` to `examples/unsupported/` with the explanatory note, and add the supported/unsupported split to the README; (8) run the standalone-consumption test below and record its evidence in PROGRESS.md. Steps 1–3 make the library importable, steps 4–6 make the examples loadable, step 7 makes the boundary honest, and step 8 proves the whole claim.

## Standalone-consumption test (the D2 proof)

The test lives in a fresh folder outside this repo (D2 creates it under `/tmp` or a scratch folder, never inside the repo) containing only two things: a copy of this repo (or the consumer-style layout — a small consumer folder whose `package.json` declares `"@codecube/photonic": "file:../photonic"` with the photonic copy as its sibling, matching the peer-checkout convention) and whatever `npm install` brings in from Photonic's declared dependencies and peer dependencies alone. No SSG files, no sibling workstreams, no `modulation` or `sonance` folders may exist anywhere in the test tree; D2 verifies this by listing the tree before running. The test page is the demo host page from step 2, served by a plain static file server, with an import map resolving `three`, `three/addons/`, and `@sparkjsdev/spark` into the installed `node_modules`. The test passes only if all of the following hold: the library entry imports with no unresolved specifier and no 404s; the `box` example loads through the new loader, its `Load` runs, and a headless browser check confirms a WebGL canvas exists, the module reports loaded, and frame callbacks tick; the `solar-system` example then loads in the same page session, proving the loader is general and not fitted to one module; the `splat` example's module graph resolves (its import of the heuristics file succeeds — rendering an actual splat is not required, because no splat asset ships with the library); and a grep gate over `src/` and the supported examples finds no occurrence of `../modulation`, `../sonance`, `../viz/`, `/script/photonics`, or `/viz/?module`. D2 records the exact commands, the tree listing, and the check output in PROGRESS.md. A failure on any one criterion is a D2 failure, not a test problem to be edited away.

## What D2 does not do

D2 does not publish anything, does not build the F1 overlay or F2 virtual camera, does not write type declarations or the final exports map (P1), and does not delete the unsupported examples — they stay in the repo, clearly labelled, because they are the reference for what a future Sonance extraction would need. DESIGN.md's known-couplings list should be updated by the D2 session to point at this plan once the work lands.
